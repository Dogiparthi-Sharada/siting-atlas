# Cleaning changelog

*Van den Broeck et al. (2005) close on documentation: "Proper documentation
should exist for each data point, including differential flagging of types of
suspected features, diagnostic information, and information on type of
editing, dates, and personnel involved." Fellegi & Holt §6.1 items 5-7 ask for
the same thing in three parts — a log of edits failed, a log of records
failing each edit, and **"the uncorrected data can be preserved and
cross-tabulated with the corrected data"**. This file is that documentation
for the defects treated on 2026-09-13, so that a reviewer — or the author in
three weeks — can see what changed and undo it without re-deriving anything.
Four fixes were written in the morning session; **Fix 5 was appended later the
same day** and is the one that turns the refusal Fix 2 installed into a frame
the warehouse can load. **Fix 6 was appended that evening** and is the only
one whose substance is a refusal: it declines to date 9 new buildings, and
finds that 76 of the 85 it was sent were already in the panel. **Fix 7 was
appended on 2026-09-14** and is the only entry that is not an edit at all: it
logs three defects in the MWPVL OCR extractor, here rather than elsewhere
because this file is the project's register of silent failures and each of the
three produced a facility row indistinguishable from a correct one.*

Every number below was measured on the files on disk, before and after.
Nothing is estimated or remembered. Paper citations are to the notes in
`docs/research/`, which were read in full.

**Reproduce the whole set of changes:**

```
  .venv/bin/python -m siting_atlas.warehouse.schema      # L2
```

## 0. Four defects, not five — and the taxonomy that merged two of them

The session brief listed the ACS top-codes and `open_quarter.fillna(1)` as
separate items. Reading Rahm & Do closes them into one.

The top-code is **not** their *embedded values* class, as
`docs/data/DATA_QUALITY.md` originally had it — embedded values means several
values crammed into one free-form field (`name="J. Smith 12.02.70 New York"`).
It is their **missing values** class, whose canonical example in Table 2 is
literally a dummy value, `phone=9999-999999`, reason "unavailable values
during data entry (dummy values or null)", with the detection rule spelled out
in Table 3: *"presence of default value may indicate real value is missing"*.

`open_quarter.fillna(1)` is the same class arriving from the other direction.
The Census substitutes $250,001; we substitute Q1. In both cases a value
stands where a measurement is absent.

Van den Broeck names why neither was ever going to be caught by a range check.
They are **erroneous inliers** — "data points generated by error but falling
within the expected range" — and he predicts the outcome exactly: *"Erroneous
inliers will often escape detection."* $250,001 is a plausible income. Q1 is a
plausible quarter. `experiments/superseded-artefacts/panel_report.json` reports both as clean
because they are, by every test the project runs.

So the two were implemented as **one declared registry**,
`src/siting_atlas/common/sentinels.py`, guarded by one build gate. Adding a
third source is adding a row to a table.

### Where the treatments sit in Van den Broeck's loop

The paper permits exactly three editing choices — correct, delete, or leave
unchanged — and insists screening is a separate act from editing. Three of the
four fixes choose **leave unchanged, and flag**. The fourth (Connecticut) is a
correction, and it is additive: the stale key is kept and a current one added
beside it. Nothing in this changelog deletes anything.

```
  fix  defect                          class                 editing choice
  --------------------------------------------------------------------------
   1   ACS codes + Q1 default          missing values /      leave unchanged
                                       erroneous inlier        + flag
   2   contradicting facility rows     contradicting records bound; refuse to
                                       (record-type scope)     manufacture
   3   flags dropped between layers    process defect        build gate
   4   Connecticut FIPS vintage        wrong references      correct, additively
   5   dates after the proven          contradicting records flag + delete
       operating date                  (cross-source scope)    the record
```

Fix 5 is the only one that takes Van den Broeck's DELETE branch, and it is the
only one entitled to: the other four found values that were *unknown*, and it
found four that are *impossible*.

## Fix 1 — substitute codes are declared once, detected once, and reach the panel

**Defect, part A.** `src/siting_atlas/ingest/census_api.py:110` (pre-fix
numbering) detected the two ACS top-codes and wrote
`median_home_value_topcoded` and `median_household_income_topcoded` into
`data/interim/acs5_zcta_2023.parquet`. `warehouse/schema.py` selected the
value columns and not the flags, so both died in L2. Nobody had ever looked
for the two bottom-codes.

**Defect, part B.** `src/siting_atlas/warehouse/facilities.py:118` (pre-fix):

```python
    frame["open_q_index"] = (frame["open_year"] * 4
                             + frame["open_quarter"].fillna(1) - 1)
```

19 of the 43 rows in `data/external/facility_panel/facilities.csv` (44.2%)
have no `open_quarter`. The `fillna(1)` was the only consumer of the NULL, so
after this line nothing downstream could tell a permit date from a convention.

**Detection.**

```
  data/interim/acs5_zcta_2023.parquet   flag columns pre-fix: 2
  data/processed/panel.parquet          flag columns pre-fix: 0
  facilities.csv rows with no open_quarter                 19 of 43 (44.2%)
  hazard_report.json event_timing/share_in_q1          0.3547 vs 0.2500
```

The Q1 artefact was found, as Van den Broeck says inliers are found, by
looking at a joint distribution rather than a range: "inliers are discovered
to be suspect if viewed in relation to other variables ... or consistency
checks". The project had measured it for months and could not act, because it
had no framework saying a distributional oddity is a screening signal that
requires a diagnosis.

**Treatment and why.** Flag, never edit. The value is left exactly as the
source gave it and a boolean records that it is a substitute:

```
  kind     detection          flag
  -------------------------------------------------------------
  TOP      value >= code      <field>_topcoded
  BOTTOM   value <= code      <field>_bottomcoded
  ABSENT   value is NULL      <field>_imputed
```

`ABSENT` is also Fellegi & Holt's **invalid-code convention** (§2 notes 3(a)
and 6): "reserve one extra code per field for all the invalid codes of Field
i", so that a record carrying one becomes a declared, countable state instead
of an arithmetic accident. That is what turns "this quarter is a convention"
into a fact in the data.

Alternatives considered and rejected:

- *Delete the top-coded ZCTAs.* Drops Palo Alto and Atherton from a siting
  model about affluent dense places. Selection on the outcome.
- *Impute a tail expectation for the codes.* Invents a number and hides the
  censoring.
- *Drop the 19 undated facility rows.* Shrinks the event count from 43 to 24
  and biases toward well-documented metros, which are the large ones.
- *Move the default to Q3 as a mid-year compromise.* Changes the target with
  no more evidence than Q1 had. `open_q_index` therefore keeps Q1: **the
  operative value is unchanged**, and choosing a different one is a modelling
  decision.

**Numbers, before -> after.**

```
  flag                                   interim   panel before  panel after
  ---------------------------------------------------------------------------
  median_home_value_topcoded                  83   column absent    83 ZCTAs
  median_home_value_bottomcoded         not comp.  column absent    20 ZCTAs
  median_household_income_topcoded            86   column absent    86 ZCTAs
  median_household_income_bottomcoded   not comp.  column absent    23 ZCTAs
  open_quarter_imputed                  not comp.  column absent   433 ZCTAs
  wage_suppressed                              0   column absent   0 of 591,200
```

In panel rows: 2,656 / 640 / 2,752 / 736 / 13,856. The ACS flags are `False`
rather than `NULL` on the 19 gazetteer-only ZCTAs with no ACS row, because the
absence of an estimate is already carried by the value column being `NULL` and
a three-valued boolean is a trap.

`wage_suppressed` was carried in the same pass: computed in
`ingest/normalise_external.py:171`, dropped by the `bls_wages` pivot, now
aggregated with `BOOL_OR`. It is `False` on all 591,200 rows where OES matched
and `NULL` on the 490,112 where no OES row exists — which is the point: it
distinguishes "BLS withheld this cell" from "this CBSA is one of the 540 of
928 that OES does not cover".

Not moved into the registry: the six large negative ACS sentinels
(`census_api.SENTINELS`). Those are Van den Broeck's **impossible** band, not
his inlier band — out of range by construction, already mapped to NULL at
read, and correct as they stand. Different diagnosis, different treatment.

**Original value retained?** Yes, everywhere. No value was changed. Recovering
the pre-fix ACS frame is dropping the four booleans; recovering the pre-fix
facility behaviour is ignoring `open_quarter_imputed`; `open_quarter` itself
keeps its `NaN` and the CSVs are untouched on disk.

**What still has to be decided.** `cost/daganzo.py:91-94` drives
`daily_parcels` through an income elasticity, so a top-coded ZCTA has its
parcel demand — and therefore its cost advantage — understated by
construction: 36 of the 2,333 ZCTAs in the published ranking on income, 46 on
home value. That file has another owner and conditioning on the flags is a
modelling decision. The note is in the docstring of
`ingest.census_api.flag_censoring` and in the panel SQL comment.

**Guarded by.** `tests/unit/test_censoring_flags.py` (6) —
`test_both_tails_are_declared_for_both_columns`,
`test_a_value_on_the_code_is_flagged_and_left_alone`,
`test_the_flags_reach_the_panel_on_the_right_zctas`. And

## Fix 2 — contradicting facility records: ranked where provenance ranks them, refused where it does not

**Defect.** `data/external/facility_panel/national_facilities.csv` holds three
pairs of rows that `common/linkage.py` matches at score 1.000 with zero false
positives, and that disagree about the opening date:

```
  NAT-0011 / NAT-0012  2815 W EL SEGUNDO BL / BLVD.    2020Q2 vs 2017Q4  (10q)
  NAT-0025 / NAT-0026  1500 E GRANT LINE / GRANTLINE   2025Q1 vs 2026Q3  ( 6q)
  NAT-0078 / NAT-0079  3610 NW SAINT HELENS / ST       2017Q4 vs 2018Q3  ( 3q)
```

`warehouse/facilities.py:206-210` aggregates catchments with
`min(open_q_index)`, so the earlier row would always win, silently.

This is Rahm & Do's **contradicting records**, and their *scope* axis explains
why nobody found it: contradictions are record-type scope, and
`experiments/superseded-artefacts/panel_report.json` reports attribute-scope statistics only.
No amount of per-column profiling surfaces them.

**Detection.** The matcher, run over the file — which the build had never
done. `tests/unit/test_linkage.py:212` ran it over the clean 43-row
`facilities.csv` and a docstring recorded that the national file has three
pairs; the test that would fail was not written. It is now
`test_the_national_panel_holds_exactly_three_contradicting_pairs`, which
reproduces all three pairs and their gaps exactly, plus "104 rows describe 101
buildings", plus the fact that all six rows are `source_type=permit`.

**Correction to the brief.** `national_facilities.csv` is read by **nothing**
in `src/` — verified by grep on 2026-09-13; the only hits are a comment in
`ingest/external.py:59` and a test docstring. The "~170 ZCTA-quarters of
target variable set by an unadjudicated conflict" is what *would* happen on
the day that file is promoted, not what is happening now. Today the figure is
zero. `facilities.csv`, the file the pipeline does read, contains no
contradicting pair, asserted by
`test_the_delivered_pilot_panel_has_nothing_to_adjudicate`.

**Treatment and why — three steps, each from a different part of the paper.**

*Step 1, what minimum-change actually settles.* Fellegi & Holt's Corollary 2
identifies the smallest set of **fields** to change and asserts satisfying
values exist. The failed edit here is

```
  E_date :  (link_score >= STREET_MATCH) AND (open_q_index_A != open_q_index_B)
```

and the two records agree on street, city, state, ZIP and geography, so the
minimal cover is the single field `open_q_index`. That is already more than
`min()` gave us — it records *that* a field was adjudicated and which one. But
§4's admissible set is uninformative: any value with A == B satisfies the
edit, so 2020Q2 and 2017Q4 are equally admissible. **Minimum change selects
the field. It does not select the date.** `DATA_QUALITY.md` R2 currently
slides from one to the other; that is the clause to fix.

*Step 2, §7 supplies the rest.* "Where there is more than one minimal set of
fields, an a priori weight of the reliability of each field could easily be
used to select among [them] ... simply take the set with the lowest product of
a priori weights", with the intuition that a simple self-coded response beats
"the product of a complicated coding operation". Here the weight attaches to
the **provenance of the date**. `facility_dedup.DATE_RELIABILITY` declares the
ranking — and it is not a new one: it is the order already written in
`ingest/facility_check.VALID_SOURCE_TYPES`, whose comment says the set is
"ordered loosely by how much weight a row deserves", read out as an explicit
rule so it can decide something. The date semantics agree with it: a press
release dates the opening, a permit is filed before the building operates and
so only bounds it from below, and `facility_check` says of OSM outright
"location only, never a date".

*Step 3, where provenance ties, stop.* §1 option 2: "one should, whenever
possible, avoid 'manufacturing' data instead of collecting it." All six rows
of the three known pairs are `source_type=permit, confidence=high`, so all
three tie, and all three are **human work, not rule work**. The pair collapses
to one facility carrying both bounds, `open_q_index` is left `NaN`, and
`facility_load.load_facilities` **refuses to load** a file that has one —
deliberately fatal, because a warning would be read once and the panel would
ship with a manufactured event date in it.

Columns produced:

```
  open_q_index_lower       the earlier bound
  open_q_index_upper       the later bound
  open_q_index             the more reliable source's date, or NaN on a tie
  open_date_contradicted   True when the two dates differ
  open_date_unresolved     True when they differ AND provenance ties
  open_date_resolved_by    "source_reliability" or "" — the audit trail
  duplicate_of             the facility_id(s) folded in
```

**Why `min()` is wrong — three objections, not one.** This replaces the
single-reason argument in the first draft of this file.

1. It is an imputation rule specified independently of the edits, the practice
   Criterion 2 exists to abolish: "it should not be necessary to specify
   imputation rules; they should derive automatically from the edit rules".
2. It is **directional**. `min()` always resolves toward the earlier date, so
   it is biased early by construction on every conflicting pair — bias in the
   outcome, not noise, over ~170 ZCTA-quarters once the file is promoted.
3. Being directional it violates Criterion 3, which asks that imputation
   maintain the frequency distribution of the variable. Taking the minimum
   shifts the whole opening-date distribution earlier.

The source semantics agree independently: a permit date is a *lower* bound on
the opening, and the minimum of two lower bounds is the loosest available. It
labels ZIP-quarters as served when they may not have been, and false positives
in the treated set attenuate every hazard coefficient toward zero — the
direction that makes a null look like a finding.

**Numbers, before -> after.**

```
                                          before        after
  national_facilities.csv rows            104           104 (file untouched)
  ... facilities after adjudication        104           101
  ... contradicting pairs recorded           0           3 (10, 6, 3 quarters)
  ... resolved by source reliability          -          0  (all tie)
  ... referred for collection                 -          3
  facilities.csv rows                       43           43
  ... adjudicated groups                   n/a           0
  enabled cells in the panel            27,914       27,914  (unchanged)
```

**Original value retained?** Yes. Both CSVs are unmodified on disk, the
collapse is reproducible by re-running the matcher, and `duplicate_of` names
the row folded in, so the grouping is invertible.

**Guarded by.** `tests/unit/test_facility_dedup.py` (12), in particular
`test_one_building_on_two_rows_is_collapsed_to_an_interval`,
`test_a_more_reliable_provenance_settles_the_date`,
`test_the_reliability_order_is_the_one_the_project_already_declared`,
`test_an_unresolved_contradiction_refuses_the_load` and
`test_the_national_panel_holds_exactly_three_contradicting_pairs`.

## Fix 3 — a build gate that fails when a computed quality flag is dropped

**Defect.** The unifying one. Fix 1's two halves are the same bug: something
upstream computes a quality signal, and the pipeline loses it between layers
with no error, because a missing column is not a failure anywhere.

**Detection.** `src/siting_atlas/warehouse/flag_gate.py`, wired into
`warehouse/panel.run()` as the `flag_gate` step after the target is attached.
Two sources of truth, on purpose:

- the **declared registry** (`common/sentinels.REGISTRY`), which catches a
  flag that was declared and whose detector never ran;
- a **suffix scan** of every `data/interim/*.parquet` footer for
  `_imputed`, `_topcoded`, `_bottomcoded`, `_censored`, `_observed`,
  `_suppressed`, which catches the ones nobody thought to declare — this is
  how `wage_suppressed` was found.

Either alone would have missed part of the defect. Parquet *footers* only, so
no column is materialised and the gate is cheap enough to run every build.

There is deliberately **no exemption list**. A flag that genuinely cannot be
carried should force a decision and a comment, not a quiet dictionary entry.

**Failing-test-first evidence.** The gate was written and run against the
then-current code before any of fix 1 was made. Verbatim:

```
  3 quality flag(s) are computed upstream and never reach `panel`:
      median_home_value_topcoded           computed in acs5_zcta_2023
      median_household_income_topcoded     computed in acs5_zcta_2023
      wage_suppressed                      computed in bls_wages
```

and as a pytest failure, once `WAREHOUSE_FLAGS` existed and before the panel
was rebuilt, `tests/unit/test_flag_gate.py::
test_no_computed_flag_is_lost_on_the_real_artefacts` reported four:

```
  E  Left contains 4 more items:
  E  {'median_home_value_topcoded': 'acs5_zcta_2023',
  E   'median_household_income_topcoded': 'acs5_zcta_2023',
  E   'open_quarter_imputed': 'data/external/facility_panel/facilities.csv',
  E   'wage_suppressed': 'bls_wages'}
```

**Numbers, before -> after.**

```
  quality flags computed upstream        3  ->  6
  ... carried into the panel             0  ->  6
  ... dropped                            3  ->  0
  panel build                    passes silently  ->  gated
```

The build now logs `flag gate: 6 computed quality flag(s), all carried into
panel` and writes `quality_flags_carried` to
`experiments/superseded-artefacts/panel_report.json`.

**Guarded by.** `tests/unit/test_flag_gate.py` (11). The mechanism is tested
on synthetic interim directories so it does not need the real data;
`test_no_computed_flag_is_lost_on_the_real_artefacts` is the one that runs
against `data/processed/panel.parquet` and skips if absent.

## Fix 4 — Connecticut's 2022 planning regions

**Defect.** Connecticut abolished its eight counties as statistical
geographies in 2022 and replaced them with nine planning regions with new
county-equivalent FIPS codes (09110-09190). The project pins ZCTA geography at
the 2020 vintage, so `data/interim/zcta_county.parquet` carries the retired
codes (09001-09015). EJScreen 2024 tract GEOIDs carry the new ones. The
county-grain join at `warehouse/optional.py:70` matched nothing for all 288
Connecticut ZCTAs — and because it is a `LEFT JOIN` onto a dense spine, it
returned `NULL` rather than an error. Rahm & Do's **wrong references**,
arriving through a real-world geography change.

**Detection.** Measured on the pre-fix panel:

```
  CT ZCTAs                                                   288
  ... with pm25, diesel_pm, traffic_proximity,
      low_income_pct, people_of_colour_pct                     0
  cells lost                              288 x 5 x 32 = 46,080
  EJScreen CT tracts, county_geoid values   09110 ... 09190 (884 tracts)
  zcta_county CT county_geoid values        09001 ... 09015 (288 ZCTAs)
```

Nobody noticed because the loss is 0.9% of panel rows and the coverage report
shows it as a national percentage.

**Treatment and why.** A second key, not an edited one. `dim_zcta` now carries
both `county_geoid` (2020, untouched) and `county_geoid_2022`, and the
EJScreen join uses the second. Sources on the old geography are unaffected and
the correction is additive, therefore reversible.

The bridge (`src/siting_atlas/warehouse/geo_keys.py`) runs at **ZCTA grain,
not county grain**, because planning regions do not nest inside the legacy
counties — both are unions of towns and the unions cut across each other.
Litchfield County (09005) alone splits three ways (Northwest Hills 28,
Naugatuck Valley 7, Western Connecticut 3), so a county-to-region crosswalk
would be wrong for 11 of the 288 ZCTAs.

The mapping comes from data already on disk: **CBP 2022 is published on the
new geography and names the planning region per ZIP**, placing 283 of the 288
directly. The 5 remaining ZIPs have no CBP row (no business establishment) and
take the modal region of their legacy county among the 283 — a rule computed
from the data, not typed from memory — recorded as `region_source = 'modal'`
so the two kinds of assignment never blur.

The nine codes and names are not from memory either: they are the intersection
of `cbsa_county.parquet` (OMB 2023 delineation, 9 CT rows) and
`building_permits.parquet` (BPS 2023-2025), which agree exactly.

Rejected: remapping `county_geoid` itself (changes a key three other layers
already trust, and flips CT's BPS permit coverage from 2018-2021 to 2023-2025
as a side effect); rolling EJScreen up to the state for CT (one value for 288
ZCTAs, which looks like data and is not).

**Numbers, before -> after.**

```
                                                  before        after
  CT ZCTAs with all five EJScreen columns              0          288
  cells filled                                         -       46,080
  distinct pm25 values in CT                           0            9  (= regions)
  bridge coverage                              -    283 cbp + 5 modal = 288
  panel rows changed                           -    9,216 (288 x 32), CT only
  pilot-metro rows changed                     -    0
  ZCTAs nationally missing pm25, by state
    CT 288, AK 245, PR 132, HI 97, +terr.  ->  AK 245, PR 132, HI 97, +terr.
```

**Original value retained?** Yes. `county_geoid` is byte-identical; the new
key sits beside it. To recover the pre-fix join, change the `ejscreen_tract`
override's `on` clause back to `b.county_geoid`.

**Still broken, reported not fixed.** The same vintage mismatch means all 288
Connecticut ZCTAs also have `cbsa_code` NULL — `cbsa_county.parquet` lists
only planning regions for CT — and therefore NULL on all five BLS wage columns
and `metro_employment`. A further 288 x 6 columns. It is outside this
session's brief and would be fixed by pointing the CBSA join at
`county_geoid_2022` as well. No Connecticut CBSA is a pilot metro
(Bridgeport-Stamford 14860, Hartford 25540, New Haven 35300, Norwich 35980,
Putnam 39480, Torrington 45860, Waterbury 47930), so it moves no published
number either way.

**Guarded by.** `tests/unit/test_geo_keys.py` (10), in particular
`test_every_connecticut_zcta_has_its_environmental_columns`,
`test_no_state_loses_ejscreen_to_a_key_mismatch`,
`test_a_zip_cbp_does_not_cover_falls_back_to_its_county_mode` and
`test_a_planning_region_is_not_split_back_into_legacy_counties`.

## Fix 5 — a declared cross-source EDIT, which resolves what the weights tied on

*Appended 2026-09-13, later the same day. Fix 2 above is correct and is not
withdrawn: where two records disagree and nothing ranks them, refusing to
guess is the right answer. This is the second edit that stops the question
arising.*

**Defect.** Fix 2 left all three national contradictions unresolved, because
all six rows are `source_type=permit` and the §7 reliability weights tie three
times. `open_q_index` is `NaN` three times and `load_facilities` refuses the
file. That refusal is sound and it is also what kept a 100-building, 62-CBSA
frame out of the warehouse while the model was fitted on 43 buildings.

What Fix 2 was missing is not a better ranking. It is a second **edit**.

```
  a Sec. 7 reliability weight    ranks two ADMISSIBLE values, and ties when
                                 the provenances match
  an edit                        declares a value INADMISSIBLE, and a
                                 contradiction does not tie
```

**The edit.** Declared in `src/siting_atlas/warehouse/edits.py` alongside the
one Fix 2 implemented implicitly, as a row in `EDITS` rather than an `if` in a
loader:

```
  E_date_contradiction   two records linked at or above STREET_MATCH must
                         carry the same open_q_index          (internal)
  E_operating_by         quarter_start(open_q_index)
                           <= osha_operating_by               (cross-source)
```

An OSHA inspection is conducted at an establishment that **exists and is
operating**, which is the reading `ingest/osha.py` has taken since it named
the column `operating_by` rather than `open_date`. So the inspection date is
an upper bound on the opening, and a record claiming the building opened
strictly after it is falsified — not outranked.

Quarter **starts**, not ends, and that is load-bearing. Portland's surviving
record claims 2017Q4 against an inspection on 2017-12-21, inside the same
quarter; an opening on 1 October satisfies both. Comparing quarter ends would
have thrown the true record away with the false one.

Matching is `common/linkage.py` — Jaro-Winkler plus the Fellegi-Sunter
three-way rule — over parsed addresses, reusing `candidate_pairs` for blocking
so the cross-source link and the within-file link are one notion of "same
building" and not two. A city join would have found none of them.

```
  facility panel                     OSHA extract                    verdict
  -------------------------------------------------------------------------
```

## Fix 7 — three row-anchoring bugs in the MWPVL OCR, each of which produced plausible wrong output and no error

**Appended 2026-09-14. This one is different in kind from Fixes 1-6 and the
difference should be said before the numbers: it is not an edit on a delivered
value, it is three defects in an *extractor*. They are logged here because this
file is the register of silent failures, and each of these three produced a
facility row that looked exactly like a correct one.**

Full pipeline write-up: [`MWPVL_OCR_PIPELINE.md`](MWPVL_OCR_PIPELINE.md). Source
document: [`MWPVL_2025.md`](MWPVL_2025.md).

**Context in one paragraph.** MWPVL's 2025 Q1 article carries its facility
tables as **images**. Rows are recovered from tesseract word coordinates by
anchoring on postal codes: every facility row ends its address with one,
nothing else in that column looks like one, and their y-centres are the row
boundaries. `src/siting_atlas/ingest/mwpvl_grid.py` does this. All three bugs
below are in that one function's neighbourhood, and all three were found by
measuring the rows that failed to anchor rather than by anticipating anything.

### 7a — midpoint banding, defeated by variable row heights

**Defect.** A row was taken to be the band between the midpoints of its
neighbouring anchors. The postal code sits on the **last** printed line of its
row, not the middle, so a row occupies the space *above* its anchor:

```
  y=2617   275 Valencia Avenue, Brea,             address, line 1
  y=2625   DJT4 | 181,500 | 2025 | Delivery...    everything else
  y=2634   California USA. 92823                  address, line 3  <- ANCHOR
```

Row heights vary with how far the address wraps — **gaps of 48 px and 64 px
measured in the same table** — so the midpoint falls above the next row's first
line, which then joins the previous facility's address. Two corrupted rows, no
error, and the row count unchanged.

**Treatment.** A word belongs to the **first anchor at or below it**, by binary
search, tolerance 8 px for the scatter of words on the anchor's own line. Words
below the last anchor join the final row rather than being dropped.

### 7b — five-digit street numbers invented facilities that do not exist

**Defect.** A US street address contains two five-digit numbers and only one of
them is a postal code:

```
  20920 Krameria Ave, March Air Reserve Base, California, USA, 92518
  ^^^^^ house number                                          ^^^^^ ZIP
```

Both match `\d{5}`. Treating the house number as an anchor **manufactures a
record** — observed as a row containing the fragment `20920 Krameria Ave, March
Air` and nothing else, while the real facility lost its first address line.
This is the one of the three that is a Rahm & Do **duplicate/spurious record**
rather than a merge, and it is the worst of them: a merge loses a facility, an
invented anchor adds one that was never there.

**Treatment.** `_ends_its_line` — a house number is followed by the street name
on the same printed line; a postal code ends the address. Position, not shape.
Testing for "leftmost" instead fails, because a postal code that wraps onto a
line of its own is both leftmost *and* rightmost.

### 7c — a table border rule broke the test that fixed 7b

**Defect.** The table is drawn with ruled borders, and a vertical rule OCRs as
`|` sitting just right of the last real word. `94561 |` therefore reads as a
postal code with something after it, 7b's test rejects the anchor, and **that
facility merges into its neighbour**. Observed on exactly that ZIP.

A fix that reintroduces the defect it was written to remove, in a narrower
form, is the reason 7b and 7c are two entries and not one.

**Treatment.** `_ends_its_line` ignores tokens with no alphanumeric character.

### Numbers, before -> after

Measured on `08_us_delivery_station`, the 535-row table:

```
                           rows   clean   merged
  before the three fixes    510     469      41     92% clean
  after the three fixes     535     517      18     97% clean
```

**Read the merge rate, not the clean rate.** 8% of rows merged before and 3%
after; the denominator moves too, because a merge deletes a row, so the two
percentages are not on quite the same base.

### Original value retained?

Not applicable in the usual sense and worth saying why. Nothing here edits a
delivered value — the fixes change how the raw image is *read*, and the PDF is
untouched. The pipeline deliberately cleans nothing: a year that reads `9022`
is written out as `9022`, because `warehouse/edits.py` can test a date against
the OSHA `operating_by` bound, which is evidence, rather than against
plausibility. That is Fix 5's argument applied to a new source.

Re-running `tools/ocr/grid_ocr.py` and
`python -m siting_atlas.ingest.mwpvl_tables` reproduces the "after" column from
the PDF. The "before" column is not reproducible from the tree — the buggy code
was replaced, not branched — which is a defect in this entry and is stated
rather than dressed up.

### Guarded by

**Nothing. There is no test file for `mwpvl_grid.py`, `mwpvl_fields.py` or
`mwpvl_tables.py`** — verified 2026-09-14 by searching `tests/` for `mwpvl`,
which returns no file. Every other fix in this changelog names a test that
would fail if the defect returned; this one cannot. The three cases above are
each a two-line fixture (a word list with coordinates), so the gap is cheap to
close and the reason it is open is that it has not been done.

A second gap in the same direction: **the merge count is not emitted into any
artefact.** `outputs/metrics/mwpvl_extraction.json` carries row counts and
per-field coverage and no merge count, so 517/535 is a working figure of the
same sort as the "13 genuinely new" facilities in `docs/STATUS.md` §4 — the
figure this project has already been burned by once. Have the ingest emit it.

## Deliberately not done

- **No outlier screen.** Rahm & Do never prescribe a distributional screen;
  Table 3 asks for min/max against a *permissible range*, a declared
  plausibility band. Winkler reframes the same thing as macro/selective
  editing — rank records by which cause the largest deviations of key totals,
  not by distance from the median. A robust-z screen puts 9,578 rows in front
  of a human and therefore never runs. When this is built it should emit Van
  den Broeck's four-way **diagnosis** (erroneous / true extreme / true normal /
  idiopathic), not a boolean. Nothing in this session touched outliers.

- **`enabled.fillna(False)` is still a collapse.** Fellegi & Holt note 6 draws
  the line this needs: "the code value 'blank' may or may not be among the set
  of possible values of a field". "Not covered by any known catchment" is a
  permissible blank; "known not to be served" is a value; the panel has them
  as the same `False`. Separating them changes the dtype and the meaning of a
  fitted target, which is a modelling decision and out of scope here. The
  invalid-code convention that would express it is declared in
  `common/sentinels.py` and is ready for it.

- **No implied-edit generation and no set-cover solver.** Theorem 1's
  guarantee requires a *complete* edit set, and a partially generated one
  gives a false guarantee rather than a weaker one. There is exactly one place
  in the project where error localisation would tell us something we cannot
  work out on paper — the three facility pairs, where the minimal cover is a
  single obvious field. The free parts of the paper (normal form, the
  invalid-code convention, the three logs, the §7 reliability weights) are
  what this session took.
