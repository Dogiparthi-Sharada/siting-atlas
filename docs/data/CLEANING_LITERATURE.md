## 1. What we had WRONG

Loudest first. Each of these was stated as fact in a project document
before 2026-09-13.

### 1.1 We filed our worst defect under the wrong class

`docs/data/DATA_QUALITY.md` F2 said of the ACS top-codes: *"This is Rahm &
Do's 'embedded values' class, and it is the clearest case in the repo of
detection without treatment."* The second clause is right. The first is
wrong.

Rahm & Do Table 2 defines embedded values with exactly one example:

> `name="J. Smith 12.02.70 New York"` — "multiple values entered in one
> attribute (e.g. in a free-form field)"

That is several distinct values crammed into one field. It has nothing to
do with sentinels. The class our top-code actually belongs to is the first
row of the same table:

> **Missing values** — `phone=9999-999999` — "unavailable values during
> data entry (dummy values or null)"

A dummy value standing in for an unavailable one. `median_household_income
= 250001` is Rahm & Do's canonical example with the digits changed. And
their Table 3 gives the detection heuristic we never ran: *"presence of
default value may indicate real value is missing"*.

This is not pedantry about a label. Getting the class right merges two
findings the audit had treated as unrelated:

```
  F2  ACS top/bottom codes    250001 (86), 2000001 (83),
                              2499 (23), 9999 (20)      census_api.py:110
  F5  open_quarter.fillna(1)  19 of 43 facilities       facilities.py:118
```

Both are dummy values occupying a field that should say "unknown". Both
survive every range check because both are *plausible values*. Van den
Broeck has the name for why they are invisible — they are **erroneous
inliers**, "data points generated by error but falling within the expected
range", and he predicts the outcome: "Erroneous inliers will often escape
detection." The Five Facets survey gives the current term of art, **hidden
missing values** (§3.3, §A.7), with `1900-01-01` for a missing date as its
worked example and a published detector, FAHES.

So: one class, one fix — a declared per-source placeholder registry, plus
the flag carried through to the panel — not two unrelated remediations.
`DATA_QUALITY.md` has been corrected.

### 1.2 Our three Fellegi-Holt "properties" are not the paper's three criteria

The previous version of this file said:

> "Three properties make it more than a style preference: the constraint
> set is *checked for consistency* before any data is touched ...; *implied
> edits* are derived automatically ...; when a record fails, the
> **minimum-change principle** picks the smallest set of fields to alter".

Every one of those three statements is true of Fellegi-Holt systems. None
of them is one of Fellegi and Holt's three criteria. Their criteria, stated
in Section 1 and quoted in full in
`docs/research/NOTES_fellegi_holt_1976.md`, are:

```
  1  minimum change      "The data in each record should be made to satisfy
                         all edits by changing the fewest possible items of
                         data (fields)."
  2  derived imputation  "It should not be necessary to specify imputation
                         rules; they should derive automatically from the
                         edit rules."
  3  distribution        "When imputation takes place, it is desirable to
     preservation        maintain, as far as possible, the marginal and even
                         preferably the joint frequency distributions of the
                         variables, as reflected by the 'correct' records".
```

We had criterion 1 and dropped 2 and 3. Criterion 2 is the one that
condemns `min()` at `facilities.py:206`, and criterion 3 is the one that
explains *why* `min()` is harmful rather than merely arbitrary. Losing them
lost the argument.

What we had listed instead were features, and there is a canonical list of
those too — Winkler RR99-01 §2, four items:

```
  1  Edit restraints reside in easily modified tables.
  2  The logical consistency of the entire edit system can be checked prior
     to the receipt of data.
  3  The main logic resides in reusable mathematical routines.
  4  In one pass through the system, records satisfy edits.
```

Goals and features are different lists and should be cited separately.

**And a second, sharper error inside the same paragraph.** `DATA_QUALITY.md`
R2 said: *"Fellegi-Holt error localisation — when records conflict, change
the minimum number of fields needed to satisfy the edits, and record which
field you changed. Here the minimum change is one date per pair."*

The first clause is correct. The last clause quietly slides from *which
field* to *which value*, and the paper does not support it. Corollary 2
identifies the minimal set of **fields** and asserts that satisfying values
*exist*. It does not choose among them. Worked out properly in §3.3 below.

### 1.3 We asserted a cost for a formal edit system that the source contradicts

The previous version of this file closed with:

> "A formal edit system in the Fellegi-Holt sense is a week and is almost
> certainly the wrong trade for a capstone."

Winkler RR99-01 §2 says:

> "FH methods show their power with small demographic surveys. If a small
> survey has reasonably well-documented edits (or at least well
> understood), then it is possible for a non-programmer to create the
> tables of edits and effectively create a production edit system in less
> than one day."

Both statements can be true, and reconciling them is the useful part — the
week is the *engine*, the day is the *edit table*. But our sentence
implied the literature agreed that formal editing is expensive, and
Winkler's position is the opposite: it is *cheaper to own* than
if-then-else rules, because the logic lives in data rather than source
code. The real argument against building one is not cost. It is in §4.

### 1.4 Three smaller corrections

**The Rahm & Do taxonomy is not a 2x2.** It is 2 (single/multi-source) x 2
(schema/instance) x **4 scopes** — attribute, record, record type, source
(§2.1). Our scorecard omitted the third axis entirely, and that omission
has a consequence: duplicated and contradicting records are *record-type*
scope, so no amount of per-attribute profiling will ever find them. Which
is exactly why `experiments/superseded-artefacts/panel_report.json` reports our data as
clean while three facility records contradict each other.

**"Missing values" is instance-level, not schema-level.** Our scorecard
filed it under SINGLE-SOURCE, SCHEMA LEVEL. Rahm & Do Table 1 has exactly
four schema-level classes — illegal values, violated attribute
dependencies, uniqueness violation, referential integrity violation — and
missing values is not one of them. It is Table 2, instance level, attribute
scope.

**Van den Broeck's author list was wrong in this document.** It read "Van
den Broeck, Cucu, Mehta & Cunningham". The authors are Jan Van den Broeck,
Solveig Argeseanu Cunningham, Roger Eeckels and Kobus Herbst.

documents had ever mentioned:

```
  1  Data analysis
  2  Definition of transformation workflow and mapping rules
  3  Verification            on a sample or copy, iterating, because "some
                             errors only become apparent after applying
                             some transformations"
  4  Transformation
  5  Backflow of cleaned data   write corrections back to the source, "to
                                avoid redoing the cleaning work for future
                                data extractions"
```

code change, and the next refresh of `national_facilities.csv` silently

Two requirements from §1 worth quoting against our own practice:

> "Mapping functions for data cleaning and other data transformations

> "To support data quality, detailed information about the transformation
> process is to be recorded, both in the repository **and in the
> transformed instances**, in particular information about the completeness
> and freshness of source data and lineage information about the origin of
> transformed objects and the changes applied to them." (§3, emphasis ours)

"And in the transformed instances" — the lineage goes in the data, not only
in a side log. Figure 3 demonstrates it by keeping both source keys on the
merged row.

### 2.2 Fellegi & Holt (1976) — the formal machinery

`docs/research/NOTES_fellegi_holt_1976.md`. Read from
`../Research/2285726.pdf`, all 20 pages including the Appendix proofs.

**What an edit is, formally.** §2, equations (2.2)-(2.3): the combination
of code values across fields which are unacceptable is a subset of the code
space, defined by a function f of per-field code subsets, and it

> "becomes an edit if, through some prior knowledge, it is declared a set
> of unacceptable code combinations, in the sense that a record a is said
> to fail the edit specified by f whenever a is in f(A_1^0, ..., A_N^0)."

Any edit reduces, by the distributive law, to the **normal form**
`INTERSECTION_{i=1..N} A_i* = F`, padded with `A_i* = A_i` for fields not
explicitly involved. The gloss:

> "any edit, whatever its original form, can be broken down into a series
> of statements of the form 'a specified combination of code values is not
> permissible.'" (§2)

**Implied edits.** The Lemma (§3): pick a **generating field** i; for every
other field intersect the code sets across the contributing edits; for the
generating field, union them. The result is an implied edit, provided no
set is empty. It is **essentially new** if the generating field's union
comes out as the *whole* code set `A_i` while every contributing edit had a
proper subset there — i.e. the new edit does not mention the generating
field at all.

Why they are needed, in one example (Winkler's version is cleaner than the
original):

```
  E1 = {age < 16, married}
  E2 = {not married, spouse}
  E3 = {age < 16, spouse}        <- implied by E1 and E2
```

A record failing E1 but not E2 looks like "change marital status" — and
every marital status value then fails E2. E3 reveals that the real conflict
is age-versus-relationship and neither of the declared edits names it.

**Complete set of edits (OMEGA)** = the explicit edits plus all essentially
new implied edits. Theorem 1 and its corollaries hold only with respect to
a complete set. Theorem 2 proves the Lemma generates everything needed.

**The minimum-change criterion, operationally.** Corollary 2:

> "We have only to select any set of fields having the property that at
> least one of them is involved in each failed edit and it then follows
> that a set of values exists for these fields which, together with the
> unchanged values of the other fields, will result in an imputed record
> satisfying all edits. If the set of fields which we select is the set
> containing the smallest number of fields (minimal set), then Corollary 2
> states that by changing the values in these fields (but keeping values in
> other fields unchanged) we will be able to satisfy all the edits."

And as an algorithm (§5.4): build the **failed edit matrix**, rows = failed
edits, columns = fields, cell = 1 if that field enters that edit
explicitly. Then

> "The problem of identifying the smallest number of fields to be changed
> to make all edits satisfied is now reduced to the problem of choosing the
> smallest set of fields (columns) which together have at least 1 in each
> failed edit (row)."

That is minimum set cover, stated in 1976 without the name.

**The consistency check.** §3 defines an inconsistent edit set as one which
"jointly imply that there are permissible values of a single field which
would automatically cause edit failures, irrespective of the values in the
other fields" — detectable as an implied edit involving only one field.
§5.2 gives the reason it matters:

> "the consistency of the edits is validated at the edit generation stage
> before data processing begins, when corrections are easily made, rather
> than at the data processing stage when, through a chance combination of
> data values, the belated discovery of the existence of inconsistencies
> could cause extensive dislocation of processing schedules."

**The invalid-entry convention**, §2 note 6, which is a two-line fix to a
bug we already found:

> "We accept a convention that whenever one of the fields of a record
> contains an invalid entry (i.e., one which is not among the set of
> possible values), we consider the record as failing all edits which that
> field enters explicitly."

**The audit trail**, §6.1 items 5-7, specified in 1976:

> "5. For each questionnaire a log can be kept of all edits failed. ...
> 6. For each edit statement a log can be kept of all questionnaires
> failing it.
> 7. The uncorrected data can be preserved and cross-tabulated with the
> corrected data."

**And the demolition of complete-case deletion**, §1, option 5 of five:

> "Option 5 would involve an implicit assumption that the statistical
> inferences are unaffected by such deletions. This is equivalent to
> assuming that the deleted records have the same distribution as the
> satisfactory records. If such an assumption must be made it would seem
> much more sensible to make it through imputation techniques."

Written in 1976, the same year Rubin published *Inference and missing
data*. It is the MCAR assumption stated before MCAR had a name, and it
arrives attached to the alternative. For a project whose default treatment
is `notna().all(axis=1)`, that is a better citation than Little & Rubin,
because it is about editing rather than about estimation.

### 2.3 Winkler RR99-01 (1999) — how it actually gets built

`docs/research/NOTES_winkler_rr99_01.md`. Read from
`../Research/rr99-01.pdf`.

**How it updates Fellegi-Holt.** It does not revise the theory; it reports
twenty-three years of implementation. Three contributions we can use.

First, it names the thing Fellegi-Holt does not: **error localisation**.
"Goal 1 is referred as the error localization problem." And it explains why
the 1976 proof is not an implementation: "FH's proof is by an inductive,
existence-type method that does not give insight into how to deal with
practical computational aspects of generating implicit edits."

Second, it reports the algorithms that made it feasible — Sande (1979)
using Chernikova's vertex-generation algorithm to avoid generating all
implicit linear-inequality edits, since "The maximum and minimum solutions
were known to occur on the vertexes"; the 60x heuristic speed-up in
Statistics Canada's GEIS; set-covering improvements by Winkler (1998) and
Chen (1998). And the systems: GEIS, SPEER, DISCRETE, SCIA, DIA, CANEDIT,
AGGIES, CherryPi, Blaise.

Third, the **cost numbers**, which are what settle §4 below:

```
  ratio edits over n fields    at most n(n-1)/2 edits total
  30 explicit edits, 10 fields ~400 implicit edits
  moderate linear-inequality
    edit set                   generation "can take 24 hours on a
                               moderately fast computer"
  250+ explicit edits          24 hours, order exp(exp(250))
  300 explicit edits           "unlikely that current algorithms can
                               generate the full set"
  small survey, edits already
    well understood, engine
    already exists             "less than one day" for a non-programmer
```

**On the practical limits of ad-hoc if-then cleaning.** This is the passage
the previous version of this document was gesturing at from memory:

> "These traditional methods include if-then-else rules for detecting
> contradictory information and various ways of imputing values of
> variables to replace the contradictory values. The dilemma with
> if-then-else rules is that they may not be straightforward to develop and
> may be difficult to write into computer code. If there are slight changes
> in the survey form and edit rules, then subsets of thousands of lines of
> code may need to be rewritten and debugged. The reason that FH methods
> are so appealing is that most of the if-then-else types of edits can be
> put in tables that are straightforward to modify and update. Because the
> source code does not need any updating, it is possible to create a FH
> system for editing that can be developed and maintained for different
> surveys by non-programmers such as subject matter specialists,
> statisticians, and economists." (§1)

Read what the objection actually is. Not that if-then rules give wrong
answers — that they are hard to make logically complete, hard to code
correctly, and catastrophically expensive to *change*, because the logic
lives in source rather than in data.

**On outlier detection.** Be careful here, because it is easy to
over-claim. **RR99-01 has no outlier-detection section.** What it has is
two paragraphs in §1 on *general methods*, and they reframe the problem
usefully:

> "General methods include selective (or macro) editing. In some
> situations, the records associated with the largest companies or firms
> can be delineated for follow-up and review. Some of these methods use
> measures such as the Hidiroglu-Berthelot (HB) statistic or graphical
> displays. HB methods involve measures that determine which records cause
> the largest deviations of key totals in the survey population. Follow-up
> is more efficient because the most important records are reviewed first."

Plus exploratory data analysis as an editing tool, and the proportionality
principle: "If only a few published totals need to be accurate, then an
efficient use of resources may be to perform detailed edits on only a few
records that effect the estimated totals."

That is the whole of it. For inliers specifically, the paper to get is
Winkler (1998) "Problems with inliers", RR98/05, which is **not** in
`../Research/`.

One more thing worth carrying, on intellectual honesty about edits.
Winkler, on an edit that flags married under-16s:

> "Application of this edit is necessarily a compromise. In a few
> situations, changing the marital status of a person who has age less than
> 16 to unmarried might induce an error. In most situations, the change
> would be a correction." (§2)

An edit is a bet, not a fact. Our `population > 0 ==> households > 0` edit
fires on 353 ZCTAs, most of which are almost certainly group quarters —
correct records we would be damaging.

### 2.4 Van den Broeck et al. (2005) — the procedure

`docs/research/NOTES_van_den_broeck_2005.md`. Read from
`../Research/pmed.0020267.pdf`.

**The three-stage loop, as they actually define it:**

> "We present data cleaning as a three-stage process, involving repeated
> cycles of screening, diagnosing, and editing of suspected data
> abnormalities. Figure 1 shows these three steps, which can be initiated
> at three different stages of a study."

Two corrections to our previous summary. It is a **repeated cycle**, not a
linear pipeline. And it can be **entered at three different points** in a
study, not only after collection.

Each stage has an explicit taxonomy, and that is what makes it usable:

```
  SCREENING   four types of oddity:
                lack or excess of data
                outliers, including inconsistencies
                strange patterns in (joint) distributions
                unexpected analysis results and other types of
                  inferences and abstractions

  DIAGNOSIS   four possible verdicts per data point:
                erroneous
                true extreme
                true normal (i.e. the prior expectation was incorrect)
                idiopathic (no explanation found, but still suspect)

  TREATMENT   three options and only three:
                "The options are limited to correcting, deleting, or
                 leaving unchanged."
```

Note that "idiopathic" is a legitimate terminal state. The framework does
not force a decision it cannot support.

**Soft and hard cutoffs** (Figure 2): two thresholds per variable, not one.
A soft cutoff flags for diagnosis; a hard cutoff is a "cutoff for immediate
diagnosis of error". Between them is a band where "diagnosis will be less
straightforward" and a combination of procedures is needed.

**When deletion IS acceptable.** The paper is more permissive than "never
delete", and precise about the conditions.

*For impossible values:*

> "Impossible values are never left unchanged, but should be corrected if a
> correct value can be found, otherwise they should be deleted."

So deletion is the *prescribed* treatment for an impossible value with no
recoverable correct value. The prohibition is on leaving it.

*For true extremes, the default is to keep:*

> "Some authors have recommended that true extreme values should always
> stay in the analysis. In practice, many exceptions are made to that rule."

*The one legitimate exception, and it carries an obligation:*

> "The investigator may not want to consider the effect of true extreme
> values if they result from an unanticipated extraneous process. This
> becomes an a posteriori exclusion criterion and the data points should be
> reported as 'excluded from analysis'."

An excluded true extreme is reclassified as a *declared scope restriction*
and reported as one. It does not silently vanish.

**When deletion is NOT acceptable:** as a default treatment for
missingness, applied without diagnosis and without reporting. The
alternative the paper offers instead of deciding is to report both ways —
"separate analyses with and without remaining outliers and/or with and
without imputation."

**Erroneous inliers**, the concept we were missing entirely:

> "A special problem is that of erroneous inliers, i.e., data points
> generated by error but falling within the expected range. Erroneous
> inliers will often escape detection. Sometimes, inliers are discovered to
> be suspect if viewed in relation to other variables, using scatter plots,
> regression analysis, or consistency checks."

And one sentence in the Diagnostic Phase that is a direct instruction to
us: **"Substitute code values for missing data should be corrected before
analysis."**

**The reporting standard**, which is a checklist we can be graded against:

> "We recommend that medical scientific reports include data-cleaning
> methods. These methods should include error types and rates, at least for
> the primary outcome variables, with the associated deletion and
> correction rates, justification for imputations, and differences in
> outcome with and without remaining outliers."

**And the small-study caveat**, which lands on a 43-row facility file:

> "In small studies, a single outlier will have a greater distorting effect
> on the results. Some screening methods such as examination of data tables
> will be more effective, whereas others, such as statistical outlier
> detection, may become less valid with smaller samples."

### 2.5 The two surveys

Read in full, lower priority, notes in `docs/research/`. Each contributed
exactly one thing that changed what we think.

**The Five Facets of Data Quality Assessment** (arXiv:2403.00526,
`NOTES_five_facets_2024.md`). A vision paper proposing five facets — data,
source, system, task, human — plus a 29-dimension glossary with assessment
challenges. What it gave us: the modern name and a detector for our defect
class (§3.3, §A.7, "hidden missing values", FAHES); the rule that
**deletions are metadata** ("transformations on missing values, like
deleted records or applied imputation strategies, must also be part of the
metadata"); and EU AI Act Article 10, which names representativity,
accuracy, completeness and relevancy as regulated dimensions. That last
gives our `rent_index` finding a legal frame — a complete-case sample whose
median ZCTA is 63.6x denser than the excluded stratum is a
*representativity* failure in the Act's sense, which is more forceful in a
defence than "MAR on density".

**A Survey of Data Quality Measurement and Monitoring Tools**
(arXiv:1907.08138, `NOTES_dq_tools_survey_2019.md`). 667 tools found, 13
evaluated against a 43-item requirements catalog. What it gave us:
empirical licence to *not* build a dimension-and-metric framework. Across
thirteen production tools including market leaders, **zero implement a
consistency metric, zero implement a timeliness metric, one implements
accuracy** (and only against a user-supplied gold standard). Two vendors
could not explain how their own metrics worked. The authors conclude:

> "In practice, DQ dimensions are used to group domain-specific DQ rules
> (sometimes referred to as metrics) on a higher level." (§5.4)

Which is the structure `DATA_QUALITY.md` already has. It also reports that
no surveyed tool does outlier detection well — four of thirteen offer only
an unlabelled plot you cannot drill into — so our F6 gap is the market's
gap, and the one tool that does it defensibly (Experian Pandora) does so by
**exposing its two thresholds as declared parameters**. That is the design
rule for R9.

### 3.1 ACS top-code flags computed then lost — 86 ZCTAs at income $250,001

`ingest/census_api.py` computes the flags. **When this section was written
they were absent from the panel's 44 columns; since 2026-09-14 they reach it,
and the panel has 50.** The prescription below was implemented as
`common/sentinels.py` plus the build gate `warehouse/flag_gate.py`, with one
clause left undone — nothing converts the sentinel to NULL and no consumer
conditions on the indicator, so the censored values are still read as
measurements. See `DATA_QUALITY.md` F2 for the measured state.

**Classification.** Rahm & Do Table 2, *Missing values*, attribute scope,
single-source instance level. Not "embedded values" — see §1.1. Van den
Broeck Box 1 and Screening Phase: an **erroneous inlier**. Five Facets
§3.3: a **hidden missing value**.

**Prescription, three papers agreeing.** Van den Broeck, Diagnostic Phase,
is the bluntest: *"Substitute code values for missing data should be
corrected before analysis."* Rahm & Do Table 3 gives the detection rule —
"presence of default value may indicate real value is missing" — as a data
profiling task, which means it belongs in the profiling pass, not in a
hand-written check. Five Facets §3.3 adds that the placeholder registry is
itself metadata: "Placeholders can differ for each data source or be
domain-specific, which is why strict documentation is important."

**So the fix is not "carry four booleans through".** It is: declare the
sentinel set per source in one place; convert sentinels to NULL plus an
explicit censoring indicator at ingest; carry the indicator to the panel;
and — Fellegi & Holt §2 note 3(a) — treat the censored state as a *code*,
not as an absence, so an edit can refer to it. The bottom-codes ($2,499
income, $9,999 home value, 23 and 20 ZCTAs) fall out of the same registry
for free.

**What the consumer then does with it** is a separate, substantive
decision. A top-coded income is a *lower bound*, and `cost/daganzo.py:91-94`
currently reads it as a point measurement feeding an income elasticity. The
options are a bound, a Tobit-style adjustment, or exclusion-with-reporting.
Nothing in the cleaning literature chooses for us; that is an econometrics
question and it belongs in `docs/METHODS_RESEARCH.md`.

### 3.2 `open_quarter.fillna(1)` — 19 of 43 facilities, 35.47% of events in Q1

`warehouse/facility_load.py:108`, moved there since this was written. **The
original NULL is no longer discarded**: `open_quarter` keeps it and
`open_quarter_imputed` reaches the panel on 433 ZCTAs. `open_q_index` still
carries Q1 and no model reads the flag, so the 35.47% is unchanged.

**Classification.** Same class as §3.1: a dummy value, an erroneous inlier,
a hidden missing value. Q1 is a perfectly plausible quarter; that is
precisely why no range check finds it.

**How it was actually detected, and what that tells us.** 35.47% of events
in Q1 against 25% expected is Van den Broeck's **third screening oddity** —
"strange patterns in (joint) distributions". The project measured it, wrote
it to `experiments/hazard-model/artefacts/hazard_report.json` under
`event_timing/share_in_q1`, and took no action. That is a screening signal
with no diagnostic stage attached to it. The framework's whole point is
that screening produces *suspects*, and a suspect with no verdict is an
unfinished job, not a finished one.

**Prescription.** Three requirements, from three papers.

*Reversibility.* Van den Broeck's first diagnostic procedure: "go to
previous stages of the data flow to see whether a value is consistently the
same. **This requires access to well-archived and documented data with
justifications for any changes made at any stage.**" We cannot do this,
because the NULL is destroyed at load. Retain `open_quarter_imputed` and
the original value.

*Do not conflate unknown with a value.* Fellegi & Holt §2 note 6: "The code
value 'blank' may or may not be among the set of possible (i.e.,
permissible) values of a field". Reserve an explicit code for "quarter not
reported" rather than borrowing Q1.

*Report both ways.* Van den Broeck, Treatment Phase and Documentation: run
the model with and without the imputed-quarter facilities and publish the
difference. That is cheaper than choosing a better default and more
convincing than defending the one we have.

The same argument applies to `facilities.py:215`'s `enabled.fillna(False)`,
which collapses "not covered by any known catchment" into "known not to be
served". Table 1 of Van den Broeck has a row for exactly this — "Value
incorrectly changed during previous data cleaning". Errors occur *during*
cleaning.

### 3.3 Three facility pairs that agree on identity and disagree on the date

`warehouse/facilities.py:206`. Disagreements of 10, 6 and 3 quarters
(Hawthorne 2020Q2 vs 2017Q4; Tracy 2025Q1 vs 2026Q3; Portland 2017Q4 vs
2018Q3).

**Classification.** Rahm & Do Table 2, **Contradicting records**, record-type
scope: "the same real world entity is described by different values". Note
that identity is *not* in question — `common/linkage.py` matches all three
pairs at score 1.000 with zero false positives, which is Fellegi-Sunter
doing its job. This is the *next* problem after linkage, and it is
Fellegi-Holt's problem, not Fellegi-Sunter's.

**The Fellegi-Holt procedure, worked out.** Six steps.

**Step 1 — declare the edit.** In normal form (eq. 2.7), over a merged
entity carrying both sources' date fields:

```
  E_date :  (link_score >= STREET_MATCH)
            INTERSECT (open_q_index_A != open_q_index_B)  =  F
```

A legitimate Type B edit: "the checking of entries in certain predetermined
combinations of fields to ascertain whether the entries are consistent with
one another." It is currently declared nowhere.

**Step 2 — error-localise.** Build the failed edit matrix (§5.4). Rows are
the failed edits; columns are fields. For each pair, the records agree on
street (after standardisation), city, state, ZIP and geography, and
disagree only on the date. So `E_date` is the only failed row and the
minimum cover is the single column `open_q_index`.

**Corollary 2 therefore says: change the date field, and change nothing
else.** That is already strictly more than `min()` provides, because
`min()` does not record that a field was changed, and a reader of the panel
cannot distinguish an adjudicated date from a reported one.

**Step 3 — recognise what Corollary 2 does NOT give you.** It asserts that
satisfying *values* exist. It does not choose one. Section 4's imputation
machinery computes the admissible set from the edits (eq. 4.2), and here
that set is uninformative: any value satisfying `open_q_index_A ==
open_q_index_B` passes, so 2020Q2 and 2017Q4 are equally admissible. **The
edits do not pin down the date.** This is the point our R2 elided.

**Step 4 — §7 supplies the missing rule.** Where more than one choice
satisfies the edits, Fellegi and Holt prescribe an *a priori reliability
weight*, and the intuition they give maps onto our sources exactly:

> "It often happens that one has an a priori belief that some fields are
> less likely to be in error than others. If one field is the product of a
> complicated coding operation and the other is a self-coded response,
> then, intuitively, one is inclined to believe that the simple self-coded
> response is more likely to be error-free. ... where there is more than one
> minimal set of fields, an a priori weight of the reliability of each
> field could easily be used to select among the minimal sets of fields the
> one to be imputed. For example, we could simply take the set with the
> lowest product of a priori weights." (§7)

For us the weight attaches to the **provenance of each date**, and the
distinction Fellegi and Holt draw is the right one: an OSHA inspection date
is a derived artefact of a regulatory process with a known and variable lag
(`docs/METHODS_RESEARCH.md` §15.1 records externally verified lags of 4, 13,
57, 69 and 345 months); a permit or press record is closer to a direct report. Declare
the ranking once, in `docs/data/FACILITY_PANEL_PROVENANCE.md`, and apply it
mechanically.

§7 also offers a less subjective alternative — "determine for each field
the proportion of edits entered by the fields which are failed" — but with
three pairs there is no signal in that and we should not pretend there is.

**Step 5 — where provenances rank equal, stop guessing.** §1, option 2:
"one should, whenever possible, avoid 'manufacturing' data instead of
collecting it." Three permit lookups. R2 already proposes exactly this, so
**R2's action was right and only its justification needed fixing**.

**Step 6 — log it.** §6.1 items 5-7: per-record log of edits failed,
per-edit log of records failing, and the uncorrected data preserved and
cross-tabulated against the corrected.

**Why `min()` is specifically wrong, in the paper's own terms.** Three
separate objections, and it is worth keeping them separate:

1. *It is an imputation rule specified independently of the edits*, which
   is the practice Criterion 2 exists to abolish and which §1 blames for
   corrections whose "net impact on the data is unforeseeable".
2. *It is directional.* `min()` always resolves toward the earlier date, so
   it is a biased estimator of the opening quarter — biased early, by
   construction, on every conflicting pair. At a median 58 ZIPs per
   station that is roughly 170 ZCTA-quarters of the target variable set by
   a systematic bias, not by an error.
3. *It therefore violates Criterion 3 as well*, which asks that imputation
   maintain the frequency distribution of the variable. Systematically
   taking the minimum shifts the whole opening-date distribution earlier.

And one operational point. Van den Broeck's small-study observation applies
here and is encouraging: with 104 national rows, "the diagnostic phase can
be cheaper and the whole procedure more complete". We can adjudicate *all*
of them. That is not true of 33,791 ZCTAs.

### 3.4 `rent_index` missing for 94.3% of ZCTAs, then complete-case deletion

**The 1976 citation is the sharpest one.** Fellegi & Holt §1, option 5:
deleting records that fail edits "would involve an implicit assumption that
the statistical inferences are unaffected by such deletions. This is
equivalent to assuming that the deleted records have the same distribution
as the satisfactory records." We can *show* that assumption fails: the
present stratum's median ZCTA has 1,555.6 households/sq mi against 24.5 in
the missing stratum.

Their conclusion — "If such an assumption must be made it would seem much
more sensible to make it through imputation techniques" — is not a
recommendation to impute here, and we should not pretend it is. They are
comparing deletion against imputation for *edit failures*, where a record
is otherwise complete. Ours is a 94.3%-missing covariate, and imputing 94%
of a column from the 6% that is a systematically different kind of place
produces a column that looks like data and is a regression prediction. The
existing judgement in §4 of `DATA_QUALITY.md` stands.

**What the cleaning literature does prescribe here, that we are not doing:**

*Report the deletion as data, not as a log line.* Five Facets §3.3 and
§A.7: "transformations on missing values, like deleted records or applied
imputation strategies, must also be part of the metadata"; "Missing tuples
can also result from previous transformation strategies, such as deleting
them if they contain missing values."

*Report the outcome both ways.* Van den Broeck: "separate analyses with and
without remaining outliers and/or with and without imputation", and the
reporting standard's "differences in outcome with and without remaining
outliers". This is the cheap, decisive move and we have never run it.

*Name it as a representativity failure.* Five Facets §A.22 and EU AI Act
Article 10. The complete-case sample's distribution does not match the
reference population's on the variable the argument turns on.

Credit where due: `rent_observed` at `warehouse/panel.py` is an explicit
availability indicator, verified equal to `rent_index.notna()`, and it is
the one place in the project where a missingness mechanism was reasoned
about before the fact. The gap is that nothing downstream conditions on it.

### 3.5 No outlier detection, and 28.36% robust-z outliers that are Manhattan

This is where the reading changed our mind most, because two papers point
away from the thing we were about to build.

**Rahm & Do do not prescribe a distributional screen.** Their detection
rule for illegal values (Table 3) is metadata-driven: "max, min should not
be outside of permissible range" and "variance, deviation of statistical
values should not be higher than threshold". That is a **declared
plausibility band per column**, not a z-score. A robust-z on household
density contains no notion of a permissible range and therefore cannot
distinguish 162,659 people/sq mi in ZCTA 10069 — which is arithmetically
and substantively correct — from an error. Running a screen with no domain
knowledge in it is why we got 9,578 flagged ZCTAs and no information.

**Winkler reframes it as prioritisation, not detection.** Macro / selective
editing does not ask "is this value extreme?" It asks which records "cause
the largest deviations of key totals in the survey population", and reviews
those first, "because the most important records are reviewed first". The
published artefact here is the 2,333-ZCTA cost ranking. So the right screen
ranks rows by **influence on the published number**, reviewed top-down
until the reviewer stops finding errors. Manhattan is high-influence and
correct, survives review once, and is never looked at again. Water Mill at
$68,623/month is high-influence and contaminated, and goes in front of a
human. A robust-z screen puts 9,578 rows in front of a human and is
therefore never run.

**Van den Broeck supplies the verdicts.** Every flagged extreme gets one of
four diagnoses, and F6's own prose already assigns them without naming
them:

```
  ZCTA 10069, 162,659 people/sq mi        TRUE EXTREME      keep
  three ZCTAs above 10,000 sq mi (AK/NV)  TRUE EXTREME      keep
  cost_per_parcel $6.41 at ZCTA 83650     TRUE EXTREME      keep
  rent_index $68,623/mo, Water Mill       ERRONEOUS         correct or,
                                            (ZORI contaminated by
                                             seasonal lettings)    failing
                                                             that, delete
                                                             and report
  permits_yoy_pct = -100%, 6,232 rows     TRUE NORMAL,      fix the
                                            prior expectation was wrong
                                            (tiny denominators)  DERIVED
                                                              VARIABLE,
                                                              not the data
  traffic_proximity = 14,529,474          IDIOPATHIC until the units
                                            question is answered
```

So **R9 should emit a diagnosis column, not a flag**, and the pipeline
should be: declared plausibility band (Rahm & Do) -> influence ranking
(Winkler) -> four-way diagnosis (Van den Broeck) -> treatment by diagnosis.
Two thresholds per column, not one — Van den Broeck's soft cutoff flags for
diagnosis, the hard cutoff diagnoses error immediately.

And whatever thresholds are chosen, the tools survey's closing demand
applies: the threshold goes in the output next to the count. "28.36% of
ZCTAs are outliers" is exactly the kind of unreproducible number that paper
documents five tools disagreeing about.

One caveat that lands on the facility panel rather than the ZCTA panel: in
small samples "statistical outlier detection may become less valid", and
"examination of data tables will be more effective". For 43 or 104 rows,
sort the table and look at it. The three contradicting date pairs would
fall out of that in a minute.

### 3.6 Seven years of vintage spread in one row, with the vintage recorded nowhere

**Classification.** Rahm & Do Figure 2, multi-source instance level,
**inconsistent timing** — the paper's own example is "current sales as of
yesterday for source 1 vs. as of last week for source 2"; ours is May-2025
wages in a 2018Q1 row. Their §2.2 also names **different aggregation
levels** separately, which is the companion defect (F7: county-grain
EJScreen under ZCTA column names, 10.5 ZCTAs per distinct value).

Five Facets gives two more precise names. §A.25 **Timeliness**: "the
difference in time between an electronically captured event in the real
world and its digital representation in the data, **considering the task at
hand**" — the trailing clause is why this matters barely for the cost model
and a great deal for a backtest that trains through 2023 on May-2025 wages.
§A.17 **Precision**, second sense, "the level of detail in information", is
the better name for 26-of-35 columns being constant across all 32 quarters:
that is not staleness, it is temporal precision we do not have.

**Prescription.** Rahm & Do §3, and the emphasis is theirs in effect:
lineage must be recorded "both in the repository **and in the transformed
instances**", including "information about the completeness and freshness
of source data". Figure 3 demonstrates it by carrying both source keys onto
the merged row. Five Facets §A.26 Traceability and §A.13 Documentation
degree say the same: provenance "and any transformation that has been
performed so far" belongs in the metadata.

Concretely that is R8 plus R10: a source-vintage table written beside the
panel, a year column in `data/interim/bls_wages.parquet` (which currently
records its vintage only in a ZIP filename), and a grain annotation on the
eight broadcast columns.

**And one detection method we do not have.** The tools survey reports
Sebastian-Coleman's suggestion of measuring consistency over time by
comparing the "record count distribution of values (column profile) to past
instances of data populating the same field". That is precisely the check
that would catch `oesm24ma.zip` being silently swapped for `oesm25ma.zip`
— hazard two under F8 — and it is requirement CDQM-42 in a 2019 commodity
tool catalog.

## 4. The open question: build a formal edit system, or not?

The old answer was a shrug with a number attached: "a week and almost
certainly the wrong trade ... the defensible version is a declared list of
constraints checked in one place, logged, with violations reported, which
is two days and captures most of the value."

The conclusion survives. The reasoning does not, and the reasoning matters,
because the old version got the cost argument backwards and did not say
what we would be giving up.

### 4.1 The cost argument does not work, and we should stop making it

Winkler RR99-01 §2 says a non-programmer can stand up a production edit
system for a small survey with well-understood edits "in less than one
day". His whole §1 argument is that formal editing is **cheaper to own**
than if-then-else rules, because the logic sits in tables a subject-matter
specialist can change rather than in "subsets of thousands of lines of
code" that must be "rewritten and debugged". If we argue from cost, the
literature argues back.

The correct decomposition is:

```
  populate an edit table, given an engine       < 1 day   Winkler RR99-01 §2
  build the engine (implied-edit generation
    + set-cover error localisation)             ~1 week
  keep the engine correct once built            see 4.2
```

The week is the engine. We would be the only user of it, on 22 edits.

### 4.2 The decisive argument is correctness, not cost

Winkler §3.1, reporting what happened when Draper and Winkler shipped a
SPEER system that generated only *some* of the implicit edits:

> "Their solution is only partially acceptable because the set of fields
> designated for change can no longer be guaranteed to be the
> error-localization solution (minimum number of fields to impute) for some
> records. **Indeed, it can no longer even assure that the solution of
> fields to change will yield a record that satisfies all edits.** The
> 'on-the-fly' method of computing implicit edits does not compute all
> implicit edits and, thus, cannot yield a proper error-localization
> solution."

And the theoretical position: "all implicit edits are always needed."

A partial Fellegi-Holt implementation does not degrade gracefully. It
returns something that *looks like* a minimum-change solution, is not, and
may not even satisfy the edits. Compared with a declared constraint list —
which makes no such claim and therefore cannot break it — a half-built
solver is **strictly worse**. That asymmetry is the argument, and it is the
one we did not have before.

Feasibility is not the issue, and we should be honest about that too. On
Winkler's own bounds, our 22 edits over ~15 numeric fields sit nowhere near
the exp(exp(250)) regime that defeats the Census — ratio edits over n
fields admit at most `n(n-1)/2` in total, which for n = 15 is 105. We
*could* generate them. It is just that there is exactly one place in this
project where error localisation would tell us something we cannot see by
inspection, and it is three facility records whose minimal cover is a
single field and is obvious on paper.

### 4.3 But the old answer dropped three things that are nearly free

"A declared list of constraints checked in one place, logged, with
violations reported" is right and incomplete. Three components of a
Fellegi-Holt system are separable from the solver, cost hours rather than
days, and we were silently omitting all three.

**(a) The consistency check on the edit set.** Winkler's feature 2: "The
logical consistency of the entire edit system can be checked prior to the
receipt of data." Fellegi & Holt §5.2 on why the timing matters: validate
"before data processing begins, when corrections are easily made, rather
than at the data processing stage when, through a chance combination of
data values, the belated discovery of the existence of inconsistencies
could cause extensive dislocation". Our 22 edits have never been checked
against each other, and one of them is already known to be broken.

**(b) The invalid-code convention.** Fellegi & Holt §2 notes 3(a) and 6:
reserve one extra code per field for invalid entries, map invalid entries
to it at load, and treat a record with an invalid entry as failing every
edit that field enters explicitly. This is a **direct fix to a bug the
audit already found**: `owner_occupied + renter_occupied == households`
currently fires on 19 ZCTAs that are in the gazetteer but absent from ACS
2023, where every field is NULL and the identity is vacuously unequal. With
the convention, those 19 stop being an arithmetic accident and become a
declared, countable state — "fails the ACS presence edit", which is a
different finding from "fails the household identity". The same convention
fixes `enabled.fillna(False)`, because "blank" becomes a code you can
distinguish from `False`.

**(c) The three logs.** Fellegi & Holt §6.1 items 5, 6 and 7: a per-record
log of edits failed, a per-edit log of records failing it, and **the
uncorrected data preserved and cross-tabulated against the corrected
data**. Item 7 is the one we would never have thought of, and it is the
answer to "what did cleaning actually do to the results?" — a question the
project currently cannot answer at all. Fellegi & Holt's own reason for
wanting it is our reason: "If it turns out that some particular edits are
failed by an inordinately large proportion of records, one would become
suspicious of either the validity of the particular edit, the field
procedures followed, or the ability of respondents to answer some
particular questions."

Three independent literatures converge on that last point, which is worth
saying out loud in a defence: Fellegi & Holt want the log for evaluation,
Van den Broeck wants it for reversibility ("This requires access to
well-archived and documented data with justifications for any changes made
at any stage"), and Five Facets wants it because "transformations on
missing values, like deleted records or applied imputation strategies, must
also be part of the metadata".

### 4.4 One more thing the reading unlocked, cheaply

Fellegi & Holt §5.1: "as far as editing only is concerned, implied edits
need not be considered — if the initially stated explicit edits all pass,
no implied edit can fail."

So a **detection-only** edit gate is complete without any of the expensive
machinery. Implied edits buy *correction*, not *detection*. If all we want
is R6 — a build gate that fails when a declared constraint is violated —
the solver is not merely a poor trade, it is irrelevant. That is a cleaner
statement of R6's scope than the one currently in `DATA_QUALITY.md`.

### 4.5 The recommendation, and the honest cost

**Build the declared constraint list. Do not build the solver. Add the
three omitted pieces.**

```
  declared edit set in code, run as a build gate      1 day
      the 22 edits in DATA_QUALITY.md F3 already
      exist as prose; they need a home, a report
      JSON, and a Makefile target

  consistency check over the edit set                 2-3 hours
      pairwise and small-subset satisfiability over
      the declared ranges.  Not FH's full implied-edit
      generation -- just: does any single field have
      a permissible value that fails an edit
      regardless of the others?

  invalid-code convention                             3-4 hours
      one reserved code per field; records with an
      invalid entry fail every edit that field enters
      explicitly.  Fixes the 19-ZCTA false positive
      and the enabled.fillna(False) collapse.

  the three logs                                      half a day
      per-record edit failures, per-edit record
      counts, and an uncorrected-vs-corrected
      cross-tab written to outputs/metrics/
                                                     ----------
                                            TOTAL   ~2.5 days
```

Against a week-plus for an engine we would use on three records, and which
would be wrong in a way that looks right if we got the implied-edit
generation incomplete.

Two caveats on that estimate, because it is an estimate.

The 22 edits in F3 are *written*, but at least one is *wrong* as written —
the household identity that fires on missingness — and nobody has reviewed
the others with the same scepticism. Reviewing 22 edits properly, with
Winkler's "an edit is a compromise" in mind, is not free and is not in the
2.5 days. Budget another half day and expect to delete two or three of
them.

And the consistency check above is a weaker thing than Fellegi & Holt's. A
genuine consistency check requires generating implied edits, because that
is how single-field contradictions surface. What is costed here is the
cheap version: check each declared range against each edit that mentions
that field. It will catch a directly self-contradictory pair and will miss
one that only contradicts through a chain of three. **Say so in the code
comment.** A check that over-claims is the same failure this whole document
is about.

## 6. What this costs, honestly

Section 4.5 gives the edit-system number: about 2.5 days, plus half a day
to review the edits themselves, and the review will probably delete some of
them.

The rest, in the order it changes a published number:

```
  carry the sentinel registry + censoring flags to the panel   1 day
      (R1, revised: a per-source placeholder registry rather
       than four ad-hoc booleans -- see 3.1)
  adjudicate the three facility dates, FH-style                1 day
      (R2, revised: declare the edit, declare the provenance
       ranking, three permit lookups, log it -- see 3.3)
  retain open_quarter's original NULL + report both ways       half a day
      (R3 -- see 3.2)
  run the cost model with and without the dropped stratum      half a day
      (new, from Van den Broeck -- see 3.4.  Cheapest
       decisive thing on this list)
  outlier screen: plausibility band -> influence rank ->
    four-way diagnosis                                         1-2 days
      (R9, redesigned -- see 3.5.  The old design was a
       robust-z report and would have been noise)
```

Nothing on that list is more than two days and several of them change a
number.

The thing that is still *not* optional is saying all of this out loud. A
model fitted on a complete-case sample that systematically excludes sparse
ZCTAs, presented without that caveat, is a stronger claim than the data
supports. And a project that answers "is your cleaning any good?" by
gesturing at papers it has not opened is making the same kind of claim.
That second problem is now fixed; the notes in `docs/research/` are the
receipt.
