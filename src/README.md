# src/ — the source tree

One package, `siting_atlas`, laid out `src/`-style. The importable name is
`siting_atlas`, **not** `src.siting_atlas` — install editable first:

```bash
pip install -e ".[dev,viz,docs]"
```

Without an install, prefix commands with `PYTHONPATH=src`.

```
  src/
    siting_atlas/          the package. Start at its README.md
    siting_atlas.egg-info/ build metadata, generated by pip
```

Every pipeline stage is a module with a `main()`, and the
[`Makefile`](../Makefile) at the repo root is the index of what you can run.
CI asserts that every module the Makefile names is importable and has a
`main()`, because the Makefile used to name three that did not exist.

**Which sub-package to read first:** `siting_atlas/README.md` has the table.
Before quoting any result the code produces, read
[`docs/NUMBERS.md`](../docs/NUMBERS.md) — it re-derives every headline figure
from the artefact that emitted it.

## House rules visible in the source

- Hand-wrapped to 79 columns so comments sit beside the code they explain;
  black is deliberately not configured.
- Modules stay under ~300 lines. Several packages have `_print`, `_report` and
  `_sql` siblings for exactly this reason, and the docstrings say so.
- Nothing hardcodes a random seed — they all come from
  `reproducibility/seeds.toml`.
- No module opens its own DuckDB connection or issues its own HTTP request;
  both go through `common/`, so every statement and every fetch lands in
  `logs/run-*/`.
